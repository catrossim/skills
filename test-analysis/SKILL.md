# 测试功能点分析

把需求转化为一份行为级、可追溯、可判定的"待验证行为清单"，供人工评审与后续测试用例派生使用。

## 产物

一次分析产出两个文件，内容同源，主文档是唯一权威源，修改先改主文档再同步导图：

- `<功能名>.test-analysis.md` — 主文档，结构按 `assets/output-template.md` 填充
- `<功能名>.test-analysis.mindmap.md` — 主文档的导图投影，格式约定见 `references/markmap-format.md`

## 层次纪律（贯穿全程的最高规则）

- 功能点 = 行为级条目，描述固定为"在 X 条件下，执行 Y，预期 Z"；预期写具体值，禁止"提示合理""符合需求"等不可判定的表述
- 来源标注只允许两种：`需求§x.x`（需求明确规定）或 `[推导]`（测试技术推导）。具体边界数据、输入组合属于下游用例层，不进功能点清单
- 需求未规定且无法推导的行为 → 写入主文档"待确认项"章节，禁止自行假设补全关键规则

## 工作流

1. 读取需求：文档路径则读取（docx/pdf 用相应读取能力）；对话描述则结合代码库浏览相关模块，补充已有行为与数据模型的上下文
2. 检查信息缺口：影响行为定义的关键信息（数值、时长、提示文案、权限规则）缺失时，列入待确认项并向用户澄清，不要假设
3. 判别功能类型并选择组织模式 → 详见 `references/organization-patterns.md`
4. 提取显式功能点：逐条对照需求，每条规则映射为一个功能点，来源标注 `需求§x.x`
5. 挖掘隐含功能点 → 详见 `references/heuristics.md`，按维度逐项检查，产出标注 `[推导]`
6. 生成主文档：按 `assets/output-template.md` 结构填充，写入用户指定路径；未指定则写入 `<repo>/docs/test-analysis/`
7. 生成导图投影：按 `references/markmap-format.md` 的 Markmap 格式输出
8. 可选渲染 HTML：命令与失败降级方式见 `references/markmap-format.md`
9. 自检与汇报 → 详见 `references/quality-checklist.md`；汇报产物路径、统计概览、待确认项清单

首次执行本技能或对输出形态不确定时，先读 `references/example-login.md` 锚定产物标准。

## 输出约定

- 编号 `FP-<MODULE>-<NN>`：MODULE 用大写英文缩写（如 LOGIN、ORDER、COUPON），全表唯一且稳定，供下游用例派生时引用回溯
- 写文件前检查同名文件是否已存在；存在则加 `-2`、`-3` 后缀，禁止静默覆盖
