# 产物自检清单与反模式

生成两个产物后、向用户汇报前，逐项过本章清单。任何一项不通过，先修复再交付。

## 条目级检查（每条功能点）

| # | 检查项 | 不合格的信号 |
|---|--------|--------------|
| 1 | 三要素完整：条件 + 操作 + 预期 | 只写了操作，如"密码错误" |
| 2 | 预期可判定：有具体值或明确行为 | "提示合理""符合需求§3.1""正常处理" |
| 3 | 来源已标注且合法 | 来源列为空，或写了 `需求§` 却找不到对应章节 |
| 4 | 编号符合 `FP-<MODULE>-<NN>` 且全表唯一 | 编号重复、MODULE 大小写混乱 |
| 5 | 类型取值在约定枚举内 | 自创类型名 |
| 6 | 层次纪律：无具体边界数据混入 | "密码 64 位上限可登录"这类用例层条目出现在功能点表（维度展开型子图内的数据形态条目除外，但需符合 organization-patterns.md 的例外说明） |

## 整体级检查

| # | 检查项 | 方法 |
|---|--------|------|
| 7 | 追溯无空洞：覆盖范围内每条需求至少对应一个 FP | 检查 §4 追溯矩阵，覆盖列为空即遗漏 |
| 8 | 范围声明完整：Out of Scope 有条目且有理由 | §1 为空且需求确实有边界外内容 → 补 |
| 9 | 待确认项闭环：每个 ⚑ 条目在 §3 有对应行，暂采用假设已写 | 交叉核对 ⚑ 与 Q 编号 |
| 10 | 统计一致：§0 的总数、P0-P3 分布与 §2 实际行数一致 | 数一遍 |
| 11 | 导图与主文档同源：`##` 分支数、叶子条目数、⚑ 标记完全一致 | 逐分支比对 |
| 12 | 粒度均匀：单条 FP 大致派生 1–5 条用例的体量 | 过粗（"登录功能可正常使用"）或过细（把边界值拆成多条）都回炉 |
| 13 | 组织模式与功能类型匹配 | 流程型却用了维度主干 → 按 organization-patterns.md 纠正 |

## 反模式（出现即修复）

1. **成功路径清单**：只有正常流功能点，无错误处理/状态迁移/权限条目 → 回到 heuristics.md 补维度 1、3、4
2. **关键词堆砌**：导图节点只有"密码错误"四个字，无编号无预期 → 导图叶子必须带 FP 编号
3. **需求复述**：把 PRD 整段复制进功能点描述 → 压缩为"条件 + 操作 + 预期"单句
4. **过度推导**：[推导] 条目数 > 显式条目的 2 倍 → 按 heuristics.md 末尾的取舍规则砍到钱/数据/权限相关
5. **模糊预期**：全文搜索"正确""合理""正常""符合需求"字样，逐一替换为可判定表述
6. **双份维护**：只改了主文档或只改了导图 → 两者条目数必须一致后交付
7. **杜撰规则**：需求没写、也不属于行业惯例的行为被写成功能点且未标 ⚑ → 移入待确认项

## 汇报格式

自检通过后，向用户汇报：

1. 两个产物的绝对路径
2. 统计概览：总数（显式/推导）、优先级分布、待确认项数
3. 待确认项清单原文（让用户逐条确认或纠正）
4. 组织模式的选择及理由（一句话）
